## 0. Контекст и как нас оценивают (читать первым)

**Задача (ТЗ 7).** По замерам сигнала построить карту покрытия района Бишкека, найти слабые зоны и предложить две площадки для новой базовой станции (БС).

**Входные данные** (выдаются в `data/`):
- `measurements.csv`: около 5000 замеров, поля `lat, lon, rsrp_dbm, timestamp`. В нём намеренно есть мусор.
- `towers.csv`: существующие БС, поля `id, lat, lon`.
- `candidates.csv`: 20 допустимых площадок для новой БС (ожидаемые поля `id, lat, lon`; проверь фактические).

**Выход (строго):**
1. HTML-карта на **Leaflet**.
2. `result.json` с ключами:
```json
{"worst_cells": [ ...3 ], "best_candidates": ["C07", "C12"], "dropped_rows": 214, "covered_weak_cells": 12}
```

**Обязательные пункты ТЗ:**
1. Очистка: отбросить дубли, замеры с RSRP вне диапазона −140…−44 дБм и замеры с координатами вне границ района. Вывести, сколько строк отброшено.
2. Сетка квадратов 200×200 м, по каждому квадрату считается медиана RSRP. Квадраты, где меньше 5 замеров, не учитываются.
3. Цвета: зелёный при ≥ −90 дБм, жёлтый от −105 до −90, красный при < −105 (это слабая зона).
4. Топ-3 худших квадрата.
5. Выбрать две площадки, которые вместе в радиусе 1 км покрывают больше всего красных квадратов без двойного учёта. Расстояние считается по формуле гаверсинуса. Площадка ближе 500 м к существующей БС не допускается.

**Бонусы:** сравнение жадного алгоритма с полным перебором пар, сравнение покрытия днём и ночью, тепловая карта.

**Проверка жюри (автопроверка, 40 баллов):** `result.json` сравнивают с эталоном на **скрытом** наборе замеров с заложенным мусором. Задача засчитывается, если пара площадок верная, `dropped_rows` совпадает с точностью ±5% и угадано хотя бы 2 из 3 худших квадратов.

## 3. Ядро: точная семантика (от неё зависит автопроверка)

> Главное правило: **данные не «чинить», а отбрасывать**. Не меняй местами lat и lon, не пересчитывай единицы, не исправляй значения. Эталон жюри, скорее всего, считает такие строки отброшенными, и любой «ремонт» уведёт `dropped_rows` за пределы ±5%.

### 3.1 Загрузка (`io.py`)
- Читать `pd.read_csv(path, dtype=str, keep_default_na=False, skipinitialspace=True)`. Всё читается строками, чтобы pandas ничего не угадывал.
- Имена столбцов: `strip().lower()`. Проверить, что обязательные столбцы на месте. Если нет, выбросить `DataValidationError` с понятным текстом (какой файл, каких столбцов не хватает).
- Числа: `pd.to_numeric(s.str.strip(), errors="coerce")`. Пустая строка, `"abc"`, `"-95 dBm"` превращаются в NaN.
- `towers.csv` и `candidates.csv` тоже валидируются. Битые строки в них логируются как warning и пропускаются, но **в `dropped_rows` они не входят** (это поле только про замеры).
- Пустой файл, отсутствующий файл или неверная кодировка: понятная ошибка и код выхода 2 в CLI, HTTP 422 в API.

### 3.2 Очистка (`cleaning.py`)
`dropped_rows = rows_total − rows_kept`, где `rows_total` это число строк данных в CSV без заголовка.

Строка отбрасывается, если выполнено **любое** из условий:
1. `lat`, `lon` или `rsrp_dbm` не парсится как число (NaN или inf).
2. `rsrp_dbm < −140` или `rsrp_dbm > −44`. Границы **включительно допустимы**: −140 и −44 остаются.
3. Точка вне границ района (по умолчанию bbox, границы включительно; если дан полигон, используется point-in-polygon, ray casting без лишних зависимостей).
4. Строка является дублем.

**Дубли.** По умолчанию дублем считается полное совпадение `(lat, lon, rsrp_dbm, timestamp)` **после** парсинга чисел (так `-95` и `-95.0` считаются одинаковыми) и `strip()` у timestamp. Первое вхождение остаётся. Набор столбцов задаётся в `config.yaml` (`dedup_subset`).
- Порядок «сначала дубли, потом фильтры» или наоборот **на итоговое число не влияет**: точные дубли либо обе валидны, либо обе нет. Для прозрачной разбивки причин делай так: сначала парсинг, потом фильтры валидности, потом дубли среди валидных.
- В лог диагностики выведи, сколько дублей получилось бы при альтернативных определениях: по всем столбцам raw-строк и по `(lat, lon, timestamp)`. Так будет видно, насколько вопрос чувствителен.

**Timestamp не является критерием очистки.** Нераспарсенный timestamp не отбрасывает строку (в ТЗ такого правила нет). Он парсится отдельно и нужен только для бонуса «день/ночь».

`CleaningReport` (dataclass): `total, kept, dropped, by_reason={"unparseable":…, "rsrp_out_of_range":…, "out_of_bounds":…, "duplicates":…}`. Сумма причин должна равняться `dropped` (каждая строка учитывается по первой сработавшей причине в указанном порядке). CLI печатает эту разбивку, как требует ТЗ («вывести, сколько строк отброшено»).

### 3.3 Геометрия (`geo.py`)
```python
R = 6_371_000.0  # м
def haversine_m(lat1, lon1, lat2, lon2) -> float | np.ndarray:  # векторизовано через numpy
    p1, p2 = np.radians(lat1), np.radians(lat2)
    dphi, dl = p2 - p1, np.radians(lon2 - lon1)
    a = np.sin(dphi/2)**2 + np.cos(p1)*np.cos(p2)*np.sin(dl/2)**2
    return 2 * R * np.arcsin(np.sqrt(a))
```
**Проекция для сетки:** локальная равнопромежуточная (equirectangular) от начала координат `origin = (lat0, lon0)`, юго-западного угла границ района:
```
y = R * radians(lat - lat0)
x = R * radians(lon - lon0) * cos(radians(lat0))
```
На масштабе района (несколько км) ошибка составляет доли процента, а формулу легко объяснить жюри. Обратное преобразование нужно для углов и центров квадратов. Квадраты в этой проекции являются прямоугольниками в lat/lon, поэтому в Leaflet рисуются через `L.rectangle`.

### 3.4 Сетка (`grid.py`)
- `col = floor(x / 200)`, `row = floor(y / 200)`, `cell_id = f"r{row}_c{col}"`. Размер ячейки берётся из конфига (`cell_size_m: 200`).
- Агрегат по ячейке: `n = count`, `median_rsrp = median` (именно **медиана**, не среднее). Сохранить также центр (`center_lat`, `center_lon`) и 4 угла.
- Ячейки с `n < 5` **исключаются из всех дальнейших расчётов**: цвета, топ-3, красные квадраты для покрытия. На карте их можно показать серым полупрозрачным слоем «недостаточно данных», он выключен по умолчанию.
- Классификация (`classify(median)`):
  - `median >= -90` даёт `green`;
  - `-105 <= median < -90` даёт `yellow` (−105 ровно считается **жёлтым**);
  - `median < -105` даёт `red` (слабая зона).

### 3.5 Топ-3 худших
Берутся все учитываемые ячейки (n ≥ 5). Сортировка по `median_rsrp` по возрастанию, при равенстве по `n` по убыванию, затем по `cell_id`. Первые 3 и есть топ-3.

**Формат в `result.json`** настраивается (`worst_cells_format` в конфиге), по умолчанию это объекты, чтобы жюри могло сопоставить квадраты по любому признаку:
```json
{"cell_id": "r12_c7", "center_lat": 42.87123, "center_lon": 74.60111, "median_rsrp": -121.5, "n": 9}
```
Альтернативы: `"id"` выводит список строк `cell_id`, `"latlon"` выводит `[[lat, lon], ...]`. Координаты округляются до 6 знаков, RSRP до 0.1.

### 3.6 Выбор двух площадок (`selection.py`)
1. **Допуск.** Кандидат исключается, если `min_dist_to_tower < 500` м (строго «ближе 500 м»; ровно 500 допускается). Для отчёта сохранить причину и расстояние до ближайшей БС.
2. **Покрытие.** `covers[c] = { cell_id красной ячейки : haversine(кандидат, центр ячейки) <= 1000 }`. Расстояние считается **до центра квадрата** (вынести в конфиг `coverage_reference: center`).
3. **Основной ответ: полный перебор** всех пар допустимых кандидатов (C(20,2) = 190 пар, это мгновенно). Метрика пары `|covers[a] ∪ covers[b]|`, без двойного учёта.
4. **Ничьи:** при равном покрытии выбирается пара с бо́льшей суммарной «глубиной» покрытых красных зон, `Σ(−105 − median)`; затем лексикографически меньшая пара id. Все пары, делящие максимум, выводятся в `report.json` и в лог как warning, чтобы было видно, если ответ неоднозначен.
5. `best_candidates` = отсортированный по возрастанию список из двух id (как в примере `["C07", "C12"]`).
6. `covered_weak_cells` = `|covers[a] ∪ covers[b]|` для выбранной пары.
7. Граничные случаи:
   - допустимых кандидатов меньше двух: понятная ошибка в лог, `best_candidates` содержит то, что есть, CLI не падает;
   - красных ячеек нет: `covered_weak_cells = 0`, пара выбирается по правилу ничьих.

### 3.7 `result.json` и `report.json` (`result.py`)
- `result.json` содержит **ровно 4 ключа** из ТЗ, в том же порядке. Всё дополнительное идёт в `report.json`, чтобы не сломать строгую проверку схемы.
- `report.json` содержит разбивку очистки, параметры конфига, статистику сетки (сколько зелёных, жёлтых и красных, сколько ячеек отброшено по n<5), всех кандидатов со статусом допуска и покрытием, все ничьи, сравнение перебора и жадного алгоритма, сравнение дня и ночи, время работы.
- JSON пишется с `ensure_ascii=False, indent=2`, числа типа numpy приводятся к Python-типам.

## 4. Карта на Leaflet (`web/`, `render.py`)

Один `app.js` работает в двух режимах:
- **Автономный** (`map.html` из CLI): данные встроены как `<script id="data" type="application/json">…</script>` и читаются через `window.__DATA__`.
- **Серверный** (`index.html` через FastAPI): данные берутся через `fetch('/api/…')`.

**Слои** (переключаются через `L.control.layers`):
1. Сетка: `L.rectangle` по углам ячейки, заливка `#2ecc71` / `#f1c40f` / `#e74c3c`, `fillOpacity ≈ 0.5`, тонкая граница. В tooltip: `cell_id`, медиана, n, класс.
2. Топ-3 худших: толстая чёрная обводка и подписи «#1», «#2», «#3» (`L.tooltip({permanent:true})`).
3. Существующие БС: маркеры и пунктирные круги радиусом 500 м (зона запрета).
4. Кандидаты: допустимые синими кружками, исключённые серыми с причиной в popup («ближе 500 м к T03: 312 м»), выбранные два крупными звёздами или зелёными маркерами, вокруг них круги 1 км.
5. Покрытые красные квадраты: выделение (например, штриховка или синяя обводка) тех красных ячеек, которые покрывает выбранная пара.
6. Бонусы: тепловая карта (leaflet.heat), слои «День» и «Ночь», слой «Хуже ночью».
7. «Недостаточно данных (n<5)»: серый слой, по умолчанию выключен.

**UI:**
- Легенда с порогами цветов.
- Боковая панель со статистикой: `dropped_rows` и разбивка по причинам, количество ячеек по цветам, топ-3 таблицей (клик по строке делает `map.flyTo`), выбранная пара и `covered_weak_cells`, таблица сравнения перебора и жадного алгоритма, сводка «день/ночь».
- Кнопки «Скачать result.json» и «Скачать map.html».
- Только в серверном режиме: форма загрузки трёх CSV (для проверки на любых данных, в том числе на скрытых) с выводом ошибок валидации.
- Центр по умолчанию: bounds данных (`fitBounds`). Тайлы OSM с атрибуцией.
- Вёрстка аккуратная, без фреймворков: чистый HTML, CSS и JS.

## 6. FastAPI (`api/`)

- `GET /` отдаёт `index.html` (статика из `web/static`).
- `GET /health` отдаёт `{"status":"ok"}`.
- `GET /api/result` возвращает `result.json` для датасета по умолчанию (`data/`). Результат вычисляется на старте и кэшируется.
- `GET /api/report` возвращает полный `report.json`.
- `GET /api/grid` отдаёт GeoJSON FeatureCollection ячеек (свойства: `cell_id, n, median_rsrp, cls, is_worst, covered`).
- `GET /api/towers`, `GET /api/candidates` (со статусом допуска и покрытием).
- `GET /api/heatmap` возвращает `[[lat, lon, intensity], ...]`.
- `GET /api/daynight` и `GET /api/compare` (перебор и жадный алгоритм).
- `POST /api/analyze` принимает multipart с 3 файлами и необязательными параметрами (размер ячейки, радиусы, пороги), возвращает полный результат. Ошибки валидации отдаются как 422 с понятным `detail`.
- `GET /api/download/result.json`, `GET /api/download/map.html`.
- Pydantic-схемы ответов в `schemas.py`, OpenAPI-документация на `/docs` (её можно показать на демо).
- Загрузка файлов ограничена по размеру (например, 20 МБ), вход валидируется, используется единый обработчик `DataValidationError` → 422.

## 7. Бонусы (максимум 10 баллов; делать после обязательной части)

1. **Жадный алгоритм против полного перебора.** Жадный шаг 1: взять кандидата с максимальным `|covers|`. Шаг 2: взять кандидата с максимальным приростом `|covers[b] − covers[a]|`. Показать результат обоих, покрытие, время работы и разницу. Добавить **юнит-тест с синтетическим примером, где жадный алгоритм проигрывает** (например, A покрывает {1,2,3,4}, B покрывает {1,2,5}, C покрывает {3,4,6}: жадный выберет A и получит 5, а оптимум B+C даёт 6). Объяснение для демо: жадный даёт гарантию (1−1/e), но не оптимум. Перебор пар стоит O(k²·m), при k=20 это мгновенно.
2. **День и ночь.** Распарсить `timestamp` (`pd.to_datetime(errors="coerce", utc=…)`). Если часового пояса нет, считать его локальным `Asia/Bishkek`. Unix epoch обработать отдельно. День задаётся как `[08:00, 20:00)`, ночь как остальное время (настраивается). Для каждой половины своя сетка с тем же порогом n ≥ 5. Сравнение: доли green/yellow/red, разница медиан по ячейкам, у которых n ≥ 5 и днём и ночью, список ячеек, которые красные только ночью или только днём. На карте слои «День», «Ночь» и «Δ (ночь − день)». Строки с нераспарсенным timestamp в это сравнение не попадают (их число указывается в отчёте), но из основного расчёта не удаляются.
3. **Тепловая карта.** leaflet.heat по очищенным замерам, `intensity = clip((−44 − rsrp) / 96, 0, 1)`, так что ярче там, где сигнал слабее. Отдельный слой с переключателем.

## 8. Тесты и качество кода (20 баллов)

Все тесты лежат в `pytest`, фикстуры в `tests/fixtures/` (маленькие CSV, ответы посчитаны вручную).

## 9. Самопроверка «как у жюри» (`scripts/make_dirty_dataset.py`)

Скрипт берёт открытый `measurements.csv`, сначала прогоняет очистку и запоминает `baseline_dropped`, затем **внедряет известный мусор** с фиксированным seed:
- точные дубли, в том числе в форме `-95` / `-95.0`;
- RSRP вне диапазона (−150, −30, 0, +10), а также граничные −140 и −44, которые должны **остаться**;
- координаты вне района, `0,0`, перепутанные lat/lon;
- пустые значения, текст в числовых полях, лишние пробелы.

Затем проверяет, что `dropped_rows == baseline_dropped + injected`, а пара площадок и топ-3 стабильны при небольшом шуме. Команда `make selfcheck`. Результат прогона кратко занести в README.
