# Демо: 3 минуты показа + 2 минуты вопросов

```bash
python run.py
```

Показать сводку: 5000 строк, отброшено 200 и разбивку по причинам (15 пустых, 15 нечисловых, 10 с неверным временем, 25 с RSRP вне диапазона, 30 вне района, 105 дублей). Сказать: `result.json` совпадает с открытым эталоном `expected.json` (это проверяет CI).

- Сетка 200 м: зелёный, жёлтый, красный; навести на клетку, показать медиану и n.

- Звёзды C09 и C14 с кругами 1 км, синие рамки — 111 покрытых красных клеток.

**1:15–1:45. Сценарий «а если владелец против?»** (веб-режим, `python run.py --serve`).

## Ответы на вероятные вопросы

**Почему RSRP вводится руками?** Браузер не даёт доступа к модему телефона. В продукте данные шли бы из нативного приложения (Android `CellSignalStrengthLte.getRsrp()`), из MDT или из лога инженерного приложения: поэтому есть импорт файла.

**Как защищаетесь от мусора в полевых замерах?** Те же правила очистки, что для CSV (один и тот же код), проверка единиц при импорте (ASU, RSSI, RSRQ), фильтр по технологии, предпросмотр без записи и отмена пакета целиком.

**Почему SQLite?** Нулевая настройка, транзакции, достаточно для одного сервера. В продукте это был бы PostgreSQL/PostGIS. На бесплатном Render диск временный, для демо этого достаточно.

**Почему полевые замеры не меняют `result.json`?** Автопроверка сверяет ответ с эталоном по скрытому набору исходных данных. Полевые замеры лежат в отдельной базе, а карта «с полевыми» считается отдельно; есть тесты, что `result.json` совпадает с эталоном до и после добавления, импорта и удаления замеров.

**Почему сценарий не меняет `result.json`?** Автопроверка сверяет ответ по ТЗ, а сценарии нужны для решений оператора. Поэтому `result.json` всегда считается без пользовательских ограничений, а сценарий лежит отдельно в `scenario.json`; есть тест, что `/api/result` не меняется после сценарных запросов.

**Как считается замена отказавшей площадки?** Тем же полным перебором, только по оставшимся парам (или по парам с зафиксированной площадкой). Это точный оптимум, а не эвристика. Если площадок сотни, пар O(k²): при k = 200 это 19 900 пар, что для множеств клеток занимает миллисекунды.


**Почему медиана, а не среднее?** Медиана устойчива к выбросам: один замер −140 в клетке не утащит её значение вниз. Среднее чувствительно к единичным провалам сигнала.

**Как строится сетка? Почему не градусы?** Переводим координаты в метры локальной равнопромежуточной проекцией от юго-западного угла района: `x = R·cos(lat0)·Δlon`, `y = R·Δlat` (в радианах), затем `ix = floor(x/200)`, `iy = floor(y/200)`. В градусах 200 м по долготе зависят от широты (на широте Бишкека 1° долготы ≈ 81.5 км, а 1° широты ≈ 111.2 км), поэтому сетка в градусах была бы не квадратной. На масштабе района (4 км) погрешность проекции — доли процента. Так же сетку определяет уточнение жюри.

**Что такое формула гаверсинуса?** Расстояние по большому кругу на сфере радиуса R = 6371 км: `d = 2R·arcsin(√(sin²(Δφ/2) + cos φ1·cos φ2·sin²(Δλ/2)))`. Евклидово расстояние по градусам неверно, потому что градус долготы короче градуса широты (в ~1.36 раза здесь).

**Почему полный перебор?** Допустимых площадок 16, пар C(16,2) = 120 (максимум C(20,2) = 190), это мгновенно (меньше миллисекунды) и даёт точный оптимум. Жадный алгоритм даёт гарантию (1 − 1/e) от оптимума, но не оптимум: на наших данных он проигрывает 3 клетки. Есть тест: A = {1,2,3,4}, B = {1,2,5}, C = {3,4,6}: жадный выберет A и получит 5, оптимум B + C = 6.

**Какая сложность?** O(k²·m): k кандидатов, m красных клеток (объединение множеств для каждой пары). При k = 20 и m = 174 — десятки тысяч операций.

**Как считается `dropped_rows`? Почему порядок фильтров не влияет?** `dropped_rows = все строки данных − оставленные`, пустые физические строки тоже считаются. Каждая строка относится к первой сработавшей причине, сумма причин равна `dropped_rows` (проверяется assert'ом и тестами). Порядок «фильтры → дубли» не меняет итог: точные дубли либо обе валидны, либо обе нет. Дубли ищем среди прошедших фильтры, первое вхождение остаётся.

**Что считается дублем?** Совпадение четырёх нормализованных полей: числа как числа (`-95` = `-95.0`), время как момент времени. Так сказано в уточнениях жюри («используйте все 4 поля»). В логе выводим, сколько дублей было бы по сырым строкам (91) и по (lat, lon, timestamp) (105) — видно, что определение важно.

**Почему не чините данные (перепутанные lat/lon и т. п.)?** ТЗ требует отбросить, а не исправить. Эталон жюри считает такие строки отброшенными, любой «ремонт» сдвинет `dropped_rows` и медианы. К тому же мы не можем знать, что исправление верно.

**Покрытие считается по чему?** По расстоянию от площадки до центра красной клетки, ≤ 1000 м включительно. Площадка ближе 500 м хотя бы к одной БС не допускается (ровно 500 м допустимо).

**Что если ничья?** Берём лексикографически минимальную пару id (правило жюри). Все пары с тем же максимумом пишутся в `report.json` и в лог; правило меняется в `config.yaml`.

**Как проверяли на скрытых данных?** `make selfcheck` внедряет 36 строк известного мусора (дубли в разной записи, RSRP −150/−30/0/+10/−140.1/−43.9, 0,0, перепутанные координаты, пустые и текстовые значения, неверное время, пустые и битые строки) и 3 граничные строки (−140, −44, лишние пробелы), которые должны остаться. Проверяем: `dropped_rows` вырос ровно на 36, пара та же, топ-3 тот же.

**Что будет, если файл битый?** CLI печатает понятную ошибку (какой файл, каких столбцов не хватает, кодировка) и выходит с кодом 2; API отвечает 422 с `detail`.
